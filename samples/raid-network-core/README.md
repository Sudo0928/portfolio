# ProjectRAID — 서버 권위 네트워크 코어 (발췌)

## 어떤 게임인가

**멀티플레이 헌팅 액션 RPG** (최대 4인 협동, PC). 여럿이 함께 거대한 몬스터를 사냥하고, 얻은 재료로 장비를 만들어 다시 더 강한 사냥에 도전하는 구조입니다. 파티를 맺어 같은 필드에 들어가고, 퀘스트를 받아 사냥을 나가고, 돌아와 제작과 보상을 정리하는 순환이 게임의 뼈대입니다.

7인 팀이 2025년 6월부터 11월까지 개발해 **GStar 2025에 출품**했습니다. 저는 네트워크 담당으로 참여했습니다. (출품 빌드는 멀티플레이 이슈로 단일 플레이 전투 버전으로 나갔습니다.)

여기 있는 코드는 그 게임에서 **파티·퀘스트·인벤토리·제작·화폐·장비가 여러 사람 사이에서 어긋나지 않게** 만드는 부분입니다.

## 읽는 순서

1. **`SceneBootstrapper.cs`** — 어느 씬에서 Play를 눌러도 NetworkManager와 매니저들이 자동 준비되는 부트스트랩 도구. 팀원 누구나 곧바로 멀티플레이 테스트를 돌릴 수 있게 했습니다. *(단독 작성)*
2. **`NetworkManagerEx.cs`** — 트랜스포트 구성과 종료 절차. 게임을 끌 때 토큰 기반 핸드셰이크(ShutdownNotice → RequestClientData → DeliveryClientData)로 접속한 클라이언트의 유저 데이터를 회수·저장한 뒤 닫습니다(타임아웃 기본 10초). **미완성 부분은 아래 회고에 적어 두었습니다.**
3. **`NetworkMessages.cs`** — 위 핸드셰이크에 쓰는 브로드캐스트 메시지 정의.
4. **`NetworkSystemManager.cs` + `NetworkSystem/`** — 기능을 도메인별 네트워크 시스템(채팅·파티·퀘스트·제작·보상·씬·유저 관리)으로 나눠 스폰하는 구조.
5. **`NetworkSystem/User/`** — 커넥션별 `UserManager`를 서버 권위로 두고 인벤토리·퀵슬롯·퀘스트·화폐·장비를 동기화. 런타임 상태는 MessagePack 영속 모델로 직렬화해 네트워크 계층과 세이브 계층을 일원화했습니다.

## 저작 범위 (정직 고지)

- `SceneBootstrapper`는 단독 작성, `NetworkManagerEx`와 `UserManager` 계열은 제가 주도했습니다.
- 일부 `NetworkSystem` 코어는 팀원과 공동 작업했습니다. 보스·몬스터 코드는 다른 팀원의 영역이라 여기 없습니다.
- FishNet은 서드파티 라이브러리로, 소스는 포함하지 않았습니다(참조만). 이 폴더 단독으로는 컴파일되지 않는 읽기용 발췌입니다.

## 지금 다시 만든다면

발췌해 두고 다시 읽어 보니 그때는 보이지 않던 것들이 보였습니다. 고치지 않은 채로 두었으므로 아쉬웠던 점을 그대로 적습니다.

**`NetworkSystemManager.GetNetworkSystem<T>()`** — 딕셔너리에 없으면 `FindAnyObjectByType<T>()`로 씬을 뒤져 캐시합니다. 그런데 씬에서도 찾지 못하면 `null`을 그대로 캐시에 넣기 때문에 이후로는 계속 `null`이 돌아옵니다. 초기화 순서가 어긋나면 조용히 실패하는 구조라, 찾지 못했을 때는 캐시에 넣지 않고 초기화 완료 여부를 먼저 확인하도록 바꾸고 싶습니다.

**`UserManager`의 `SyncVar<UserInventory>` 계열** — 하위 컴포넌트의 *참조*를 SyncVar로 동기화하고 있습니다. 같은 프리팹 안에 있어 클라이언트도 `GetComponentInChildren`으로 직접 얻을 수 있으므로 참조를 네트워크로 보낼 필요가 없었습니다. SyncVar는 실제로 값이 바뀌는 데이터에만 쓰는 것이 맞습니다.

**`UserManager.Init()`** — 인벤토리·퀵슬롯·기록·퀘스트·화폐·대화·장비 초기화가 한 함수에 나열되어 있어, 유저 데이터가 하나 늘 때마다 이 함수를 고쳐야 합니다. 공통 인터페이스를 두고 목록을 순회하는 방식이 낫습니다.

**`NetworkSystemManager.Initialize()`** — `UniTask<bool>`을 반환하지만 반복문을 한 번에 다 돌고 `UniTask.FromResult(true)`를 돌려줍니다. 비동기 시그니처인데 실제로는 동기라, 스폰 대상이 늘어나면 그 프레임이 통째로 멈춥니다.

**`NetworkManagerEx` (354줄)** — 트랜스포트 구성, 서버 시작·종료, 종료 핸드셰이크, 브로드캐스트 등록, 강제 퇴장을 한 클래스가 맡고 있습니다. 종료 절차만 따로 떼어내고 연결 상태 관리만 남기는 편이 좋겠습니다.

**원격 트랜스포트가 연결되어 있지 않습니다 (`NetworkManagerEx.cs:197-198`).**

```csharp
if (Managers.Instance.DebugMode) Multipass.SetClientTransport<Yak>();
else Multipass.SetClientTransport<Yak>();
```

if와 else가 같은 코드입니다. `Tugboat`는 18행의 `using` 선언에만 있고 어디에서도 호출되지 않습니다. Yak은 같은 프로세스 안에서만 도는 로컬 트랜스포트이므로, 이 상태로는 원격 접속이 성립하지 않습니다. 당시에는 로컬에서 클라이언트를 여러 개 띄워 테스트하는 데 집중했고 원격 경로를 끝까지 연결하지 못했습니다. 발췌를 정리하면서 발견하였고, 관련 서술은 전부 정정하였습니다.

**`OpenServer(int maxMembers = 4)`의 본문이 비어 있습니다.** 주석 한 줄만 남아 있어 실제로 하는 일이 없습니다. 최대 접속 인원 4는 이 함수가 아니라 36행의 `MaxConnectionCount = 4` 필드가 근거입니다.

**종료 핸드셰이크의 실패 경로가 없습니다.** `BeginShutdown`이 10초 타임아웃 뒤 `false`를 돌려주지만, 그것을 받은 쪽은 그대로 연결을 닫습니다. 응답하지 못한 클라이언트의 데이터는 유실됩니다. 재시도나 부분 저장 같은 대비가 필요합니다.

**`_token`을 서버와 클라이언트가 함께 씁니다.** 호스트 모드에서는 한 인스턴스가 양쪽 역할을 모두 하기 때문에 같은 필드를 서로 덮어쓸 수 있습니다. 역할별로 상태를 나누어야 합니다.
